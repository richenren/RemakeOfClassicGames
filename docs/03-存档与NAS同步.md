# 本地存档与 NAS 同步设计

## 1. 已确认方向

**离线优先 + 多存档槽 + 定时快照 + 关键事件保存 + NAS 异步同步。** 这不是联网实时对战，不需要 WebSocket、Redis、Kafka 或持续上传战斗帧状态。

### 保存与同步频率

- **本地：约每 5 秒保存一次**当前存档的可恢复快照。
- **NAS：在线时约每 15–30 秒同步一次**最新有效快照。
- 关键事件（升级选择完成、法坛完成、单局结束、境界突破、解锁变化、重置存档等）立即触发本地保存，并尝试立即同步；同步不得阻塞战斗。
- 手机后台杀进程可能不触发退出钩子，因此不能只依靠退出保存。
- 发生磁盘写入失败要反馈，不能把“本地保存成功”误认为“NAS 同步成功”。

以上为目标频率；实现时需考虑写入合并、移动端电量、NAS 不在线和同步失败重试。

## 2. 多存档槽模型

每个存档槽是完全独立的游戏进度单元，分别保存：
- 功德与境界。
- 已解锁的技能、法器、主动道术及内容。
- 已完成试炼、尸王首次通关/精魄记录、通关记录。
- 已解锁内容的随机池启用/禁用配置。
- 当前局快照（如有）。

规则：
- 新建多个存档槽后，任何一个槽的成长、解锁和配置都不得影响其他槽。
- “重新开始本局”只重置当前局快照和局内资源，保留该槽的功德、境界、解锁、试炼与通关记录。
- “重置整个存档”清空所选槽全部数据，不影响其他槽；必须有明确二次确认。
- 同一存档原则上不允许多个设备同时写入。跨设备切换时，先完成同步/释放写入权；无法确认时提示玩家，不静默覆盖。
- 设备设置（音量、画质、帧率、触控布局等）默认保存在本地，不随存档同步。

## 3. 存档内容分层

### 3.1 存档槽持久进度

持久数据包括功德、境界、解锁内容、卡池启用状态、试炼进度、首通标记和历史记录。具体字段以游戏实现时的 schema 为准。

### 3.2 局内快照

建议保存：
- 当前局 ID、存档槽 ID、快照 schema 版本。
- 关卡/地图标识、已过时间、随机种子（如确有必要）。
- 玩家位置、生命、护盾、等级、经验、治疗次数。
- 当前主动道术、攻击技能与等级/分支/进化状态、法器与等级、通用强化。
- 法坛解锁/完成/净化进度、Boss 阶段与状态、关键掉落和任务状态。
- 生成器阶段和必要的生成器状态。

不要求保存每只敌人、每个投射物的逐帧状态。若恢复时重建敌人，应使用确定性规则或明确标记为近似恢复，并在恢复后提供短暂无敌保护，避免重建敌人立即造成不可避免的伤害。

### 3.3 数据示意

以下仅为结构示意，字段可随实际实现调整：

    {
      "schema_version": 1,
      "slot_id": "profile_01",
      "revision": 12,
      "saved_at": "2026-10-22T09:00:00Z",
      "progress": {
        "merit": 0,
        "realm": "入道",
        "unlocks": [],
        "enabled_pool": [],
        "trial_progress": {},
        "first_clear_flags": {}
      },
      "run_snapshot": {
        "run_id": null,
        "stage_id": null,
        "elapsed_seconds": 0,
        "player_state": {},
        "build": {},
        "event_state": {}
      }
    }

revision 由服务端维护，客户端上传 base_revision；客户端时间仅用于显示，不可作为冲突优先级。schema_version 支持未来迁移。

## 4. 同步时序与冲突保护

1. 启动：加载并校验本地快照；若联网且已授权，查询 NAS 远端版本。
2. 版本一致时可继续；存在不同分支时提示玩家选择或恢复历史版本，**不能静默覆盖**。
3. 玩游戏：本地先安全写入；SyncManager 将最新快照放入待发送队列。队列可合并同一存档的旧待发送快照。
4. 上传：携带 slot_id、base_revision 和客户端唯一请求 ID（幂等键）；服务端在事务内校验版本并递增 revision。
5. 失败：保留本地快照并指数退避重试；HTTP 409 冲突时重新获取远端版本，进入冲突解决流程。
6. 跨设备切换：新设备拉取最后成功提交的云快照。上一设备未成功上传的变化不能保证零损失，因此 UI 必须明确展示最近同步状态。
7. 同一存档写入权：服务端需要提供轻量的写入租约/设备占用标记，或者等价的单写者保护；租约失效和异常退出的回收规则需在 V0.2 实现阶段验证。

## 5. API 草案

| 方法/路径 | 用途 |
| --- | --- |
| POST /api/auth/login | 家庭玩家身份验证或设备配对 |
| GET /api/saves/{slot_id} | 获取当前用户有权限访问的存档快照 |
| PUT /api/saves/{slot_id} | 带 base_revision 和请求 ID 的条件更新 |
| GET /api/saves/{slot_id}/history | 获取有限历史版本，用于手动恢复 |
| GET /health | 内部健康检查，不包含私密数据 |

响应建议返回 updated revision、server timestamp、checksum。API 不信任客户端传入的 player_id 即授权身份。

## 6. 服务端技术与部署

- **FastAPI + SQLite**：家庭少量玩家的 CRUD 足够；SQLite 文件放 NAS 持久化目录，不放临时容器层。
- NAS：部署前确认具体机型、DSM 和 Container Manager 支持。
- 接入：个人设备优先使用已建立的 ZeroTier 私有网络，配置受信任 HTTPS/TLS。若日后供非 ZeroTier 手机使用，需要有身份认证、TLS 和受控公网入口。
- 安全：令牌安全保管、速率限制、参数校验、最小权限；不将数据库端口、NAS 管理端口或无鉴权 API 直接开放公网。
- 备份：定期将 SQLite 一致性备份到另一介质/位置；RAID 不是备份。保留有限历史快照。
- 数据迁移：按 schema_version 管理，升级前备份，客户端可识别不兼容快照并提示。

## 7. 版本范围

### V0.1：本地多存档

- Windows 与 Android 可运行核心战斗。
- 本地多存档槽、独立进度、存档重置保护。
- 本地约每 5 秒保存；关键事件立即保存。
- 支持当前局快照恢复与 schema 版本标记。
- NAS 同步暂不作为 V0.1 验收条件。

### V0.2：NAS 同步

- FastAPI + SQLite 部署到 NAS。
- 约每 15–30 秒异步同步；关键事件触发同步尝试。
- 版本校验、单写者保护、冲突提示、历史备份、离线重试。
- 显示本地保存与云端同步状态，明确区分两者。

## 8. 验收清单

- 两个存档槽各自解锁/升级后互不影响。
- 重新开始本局保留长期成长；重置一个槽不影响其他槽。
- 本地定时保存与关键事件保存均有效。
- NAS 不在线时游戏继续，本地存档有效，UI 显示未同步。
- Windows/Android 交替使用同一存档时，旧 revision 上传被拒绝并进入冲突流程，不静默丢失任一端快照。
- 同一存档同时被两个设备写入时，单写者保护生效。
- 突然断电/进程被系统终止后可从最后成功的本地快照恢复。
- 重建战场后不会因敌人瞬间刷新造成不可避免伤害。
- 重复请求 ID 不会重复应用进度变更。
- 数据损坏可从上一份有效快照或 NAS 历史恢复。
