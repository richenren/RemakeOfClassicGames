# 技术选型与架构（已确定技术方向）

## 1. 目标与边界

目标是单人业余开发一款 2D 俯视角幸存者式肉鸽游戏，Windows 与 Android 可运行；保留 iOS、实体摇杆、本地双人模式的演进空间。游戏内容尚未确定。仅做家庭游戏，不需要账号中心、在线战斗或大型分布式系统。

### 必须具备

- 统一核心战斗逻辑；输入、UI、安全区与性能按平台适配。
- 离线运行、可恢复的本地存档，联网时通过 NAS 同步。
- 使用免费优先的工具，尽量不引入运行时付费依赖。
- 保持可扩展性，但不提前引入复杂 ECS、微服务、Redis、消息队列。

### 非目标（当前）

- 实时多人对战、服务器权威帧同步、竞技反作弊。
- 商业运营、付费、跨公网开放注册。
- 忠实还原原作受保护的画面/音频/角色。

## 2. 方案对比与结论

| 方案 | 优势 | 主要代价 | 结论 |
| --- | --- | --- | --- |
| Godot 4 + GDScript | 免费开源、2D 工作流成熟、Windows/Android/iOS 导出、游戏专用编辑器 | 需要学习 Godot 场景/节点/资源体系 | **采用** |
| Unity + C# | 成熟生态和资产商店 | 编辑器与工程较重、授权规则需持续关注 | 备选 |
| Cocos Creator + TypeScript | TS 生态、移动与小游戏友好 | 桌面原生游戏工具链需评估 | 备选 |
| Phaser + TypeScript | Web 开发体验熟悉 | 移动/桌面封装、原生集成成本 | 不优先 |

游戏本体选 Godot 4 **稳定版本** + GDScript；渲染首选 Compatibility 并以目标 Android 真机为准。版本锁定前核对官方导出要求与插件兼容。Godot MIT 开源，不收引擎订阅费或销售分成，第三方服务/素材可能收费。

## 3. 游戏工程逻辑分层

- **场景层**：Main、World、Player、Enemy、Projectile、HUD、Menus；以 Node2D/CharacterBody2D/Area2D/Control 等组织，按实际需求选节点。
- **核心规则**：游戏状态（菜单/进行/暂停/结算）、战斗伤害与状态、敌人生成、经验升级与随机候选、武器效果、关卡进度。
- **数据层**：自定义 Resource 储存角色、武器、敌人、升级条目的静态定义；避免到处根据字符串写巨大 if/else。
- **输入层**：InputMap 抽象 move 等动作；PC 键盘、USB 手柄/摇杆、移动端虚拟摇杆映射至相同指令。不要把设备判断耦合到 Player。
- **持久化层**：SaveManager 管理游戏状态快照与 schema_version；SyncManager 仅负责上传/下载/冲突处理，不能卡住主循环。
- **表现层**：精灵、动画、粒子、声音、摄像机与 UI；尽量让表现与伤害数值分离。
- **平台适配**：触屏控件、安全区、横屏设置、分辨率/画质策略、生命周期（移动端可能直接被系统终止）。

## 4. 跨端与性能原则

- 初步采用横屏 16:9 布局，但 UI 应对异形屏、安全区、不同纵横比；正式方向仍可在游戏内容确认时修改。
- 自动攻击游戏的手机交互以虚拟移动摇杆为主，升级选项适配触控。
- 初始验收目标为 PC 60 FPS、中端 Android 尽可能稳定 60 FPS；低端设备可降低至 30 FPS/缩减特效。这是目标，不是任何设备的性能保证。
- 从数十敌人做起，测试 100–200 同屏实体；用 Profiler 确定瓶颈，再优化碰撞、频率、对象池、可见性、绘制，不做过早复杂优化。
- 提前防范：长时间游玩内存增长、移动端暂停恢复、触摸误触、后台切换、音频焦点变化。
- Android 在 Windows 开发环境使用 Godot + JDK/Android SDK 导出 APK；iOS 通常需要 macOS 与 Xcode、签名及设备验证。

## 5. 服务端位置

服务端不是运行战斗模拟的服务器，而是存档服务：FastAPI + SQLite，通过 Docker/Container Manager 在群晖 NAS 上运行。使用 HTTPS 或家庭虚拟专网（如 ZeroTier）受限访问。API 与存档细节见 [存档文档](03-存档与NAS同步.md)。
